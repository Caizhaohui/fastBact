# fastBact — Claude Opus 5.5 Architecture & State Semantics Review

## Context & Objectives

You are performing an independent, authoritative graph state semantics and architectural safety review for fastBact repeat resolution (exSPAnder subsystem) on commit `37a7c0baeb251e6211beafc60a2608304916a0f6` (`feature/c0-02r-phase-f7-grok`).

### Background: Finding F8-P1-001
In the Phase F8 Codex independent audit (`AUDIT-20261021-005`), a P1 correctness defect was identified in Phase F7's external neighbor preservation logic:
- In `src/resolve/exspander.rs`, `rejected_nodes: HashSet<u32>` was historically used for two distinct purposes:
  1. Excluding rejected candidate paths during BFS search (`exspander.rs:246`: `if rejected_nodes.contains(&u.id()) { continue; }`).
  2. Protecting unmerged short unitigs (< 500 bp) from orphan cleanup at Stage 5 (`exspander.rs:1051`: `if !rejected_nodes.contains(&node.id) ... { node.is_deleted = true; }`).
- In Phase F7, when a path was successfully validated and committed, all unconsumed external neighbors incident to any constituent node were inserted into `rejected_nodes` (`exspander.rs:997`) to shield them from Stage 5 orphan cleanup.
- **Defect**: This conflated cleanup protection with candidate rejection. When an external neighbor $X$ of an earlier committed path $S_1 \to R$ was inserted into `rejected_nodes`, a subsequent seed $S_2$ exploring a fork at $Q$ ($Q \to X$ vs $Q \to D$) silently skipped $X$ during BFS dequeue because `rejected_nodes.contains(&X.id()) == true`.
- Search returned `SearchStatus::Complete` because the queue drained normally, and fastBact committed the weaker alternative $D$ via single-candidate acceptance ($W/C \ge 0.05$), while the authentic supported path through $X$ was never evaluated.

Codex proposed a minimal repair: split `rejected_nodes` into two separate sets:
- `rejected_nodes: HashSet<u32>` (strictly for failed candidate path rejections, checked in BFS).
- `cleanup_protected_nodes: HashSet<u32>` (strictly for Stage 5 orphan cleanup protection, never checked in BFS).

Your mandate is to perform an authoritative architectural review to determine whether this minimal two-set split is fundamentally sound, complete, and sufficient, or whether deeper state lifecycle refactoring is required.

### 1. State Semantics Contract & Lifecycle Matrix
Formulate a formal State Semantics Matrix covering at least:
- `SEARCH_REJECTED`
- `CLEANUP_PROTECTED`
- `CONSUMED`
- `DELETED`
- `VISITED_IN_SEARCH`

For each state, define:
- **Owner**: Which function/subsystem owns and manages this state?
- **Writer**: Exactly when and under what preconditions is this state applied?
- **Reader**: Exactly which components consult this state, and what decisions are gated on it?
- **Lifecycle**: When is it instantiated, when does it transition, and when is it cleared?
- **Allowed Transitions**: What subsequent states can a node transition to?
- **Invalid Transitions**: What state transitions are strictly prohibited?
- **Effect on Candidate Eligibility**: Does this state exclude or alter BFS search?
- **Effect on Cleanup**: Does this state shield from Stage 5 deletion?
- **Effect on Sequence Preservation**: Does it guarantee node sequence survival?

Specifically answer:
- **Q-A**: Does `cleanup_protected_nodes` completely avoid affecting BFS candidate search?
- **Q-B**: Should `rejected_nodes` still provide cleanup protection at Stage 5, or should failed candidates be eligible for orphan deletion?
- **Q-C**: Can a single physical node legitimately belong to both `SEARCH_REJECTED` and `CLEANUP_PROTECTED` simultaneously? If yes, what is the resolved behavior?
- **Q-D**: Does the resolver-wide lifetime of `rejected_nodes` across multiple seed extensions introduce hidden cross-seed coupling? If a candidate path was rejected during exploration from seed $S_1$, is it valid to permanently ban that node from candidate exploration when starting from seed $S_2$?
- **Q-E**: When a cleanup-protected node is subsequently incorporated into a splice by a later seed, does it transition to `CONSUMED`/`DELETED`, and does its presence in `cleanup_protected_nodes` create any contradiction?
- **Q-F**: Is there any risk of over-protection where sequencing noise / dead tips connected to committed paths are improperly immortalized?
- **Q-G**: If graph validation or splicing fails (`validate_and_splice_path` returns `Err`), is failure atomicity strictly guaranteed for all sets?
